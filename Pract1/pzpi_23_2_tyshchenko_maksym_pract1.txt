2 ЗАВДАННЯ  
2.1 Мета роботи
Метою практичного заняття є ознайомитися з одним із шаблонів (патернів) проєктування програмного забезпечення, проаналізувати його структуру, призначення та практичне застосування.
Відповідно до завдання необхідно:
* Підготувати доповідь на тему: «Шаблон (патерн) проєктування ПЗ: Strategy (Стратегія)»
* Обрати шаблон (патерн) із книги GoF (крім Singleton).


3 ОПИС ВИКОНАНОЇ РОБОТИ 
3.1 Загальні відомості про шаблони (патерни) проєктування
Шаблони (патерни) проєктування — це перевірені часом, типізовані архітектурні рішення для поширених проблем, що виникають під час розробки програмного забезпечення. Вони не є готовими фрагментами коду чи бібліотеками, які можна просто скопіювати в проєкт. Патерн — це скоріше загальна концепція, алгоритм або схема взаємодії класів та об'єктів, яку розробник адаптує під специфіку власної задачі.
Історично концепція патернів була запозичена з архітектури (праці Крістофера Александера), але справжню популярність у сфері ІТ вона здобула у 1994 році після виходу книги «Design Patterns: Elements of Reusable Object-Oriented Software». Її автори — Еріх Ґамма, Річард Хелм, Ральф Джонсон та Джон Вліссідес, відомі у спільноті як «Банда чотирьох» (Gang of Four, або GoF). Вони систематизували 23 класичні патерни, що стали фундаментом об'єктно-орієнтованого проєктування (ООП).
Основне призначення патернів
* Стандартизація коду: Використання єдиних підходів до вирішення типових задач.
* Спільний словник розробників: Замість того, щоб довго пояснювати архітектуру, програмісту достатньо сказати «я використав тут Фабрику та Спостерігача», і колеги одразу зрозуміють структуру коду.
* Підвищення гнучкості: Патерни допомагають писати код, який легше масштабувати, підтримувати та змінювати в майбутньому (зокрема, дотримуючись принципів SOLID).
Класифікація патернів GoF
Залежно від того, яку саме проблему вирішує шаблон, їх поділяють на три великі групи:
1. Породжувальні (Creational patterns) Ці патерни відповідають за процес створення об'єктів. Вони приховують логіку інстанціювання, що робить систему незалежною від того, як саме створюються, компонуються та представляються її об'єкти.
* Суть проблеми: Пряме створення об'єктів через оператор new часто призводить до жорсткої прив'язки (coupling) класів один до одного.
* Як вирішують: Пропонують механізми динамічного створення об'єктів залежно від ситуації.
* Типові представники:
   * Factory Method (Фабричний метод): Делегує створення об'єктів підкласам.
   * Abstract Factory (Абстрактна фабрика): Створює сімейства пов'язаних об'єктів.
   * Builder (Будівельник): Дозволяє покроково створювати складні об'єкти.
   * Prototype (Прототип): Створює нові об'єкти шляхом клонування існуючих.
2. Структурні (Structural patterns) Визначають, як з класів та об'єктів утворюються більші, складніші структури, зберігаючи при цьому гнучкість та ефективність.
* Суть проблеми: Як організувати класи так, щоб зміна однієї частини системи не ламала інші, і як змусити несумісні інтерфейси працювати разом.
* Як вирішують: Використовують спадкування для складання інтерфейсів (на рівні класів) або композицію для динамічного зв'язування (на рівні об'єктів).
* Типові представники:
   * Adapter (Адаптер): Дозволяє об'єктам із несумісними інтерфейсами працювати разом.
   * Facade (Фасад): Надає простий інтерфейс до складної підсистеми.
   * Decorator (Декоратор): Динамічно додає об'єктам нові обов'язки без використання підкласів.
   * Composite (Компонувальник): Дозволяє згрупувати об'єкти у деревоподібні структури та працювати з ними так само, як з одиничними об'єктами.
3. Поведінкові (Behavioral patterns) Фокусуються на алгоритмах та розподілі обов'язків між об'єктами. Вони описують не лише структуру, але й саму взаємодію — те, як об'єкти обмінюються повідомленнями.
* Суть проблеми: Заплутана логіка взаємодії, масивні умовні оператори та жорстка залежність алгоритмів від класів, що їх використовують.
* Як вирішують: Інкапсулюють алгоритми, стани або запити в окремі об'єкти, налаштовуючи гнучку комунікацію.
* Типові представники:
   * Strategy (Стратегія): Дозволяє динамічно змінювати алгоритм поведінки об'єкта.
   * Observer (Спостерігач): Створює механізм підписки, щоб одні об'єкти могли слідкувати за змінами стану інших.
   * State (Стан): Дозволяє об'єкту змінювати свою поведінку залежно від внутрішнього стану.
   * Command (Команда): Перетворює запити на об'єкти, що дозволяє передавати їх як аргументи, ставити в чергу або логувати.
Область застосування
Шаблони проєктування не є обов'язковими для кожної програми. Їх застосування є доцільним у середніх та великих проєктах, де складність бізнес-логіки вимагає чіткої архітектури. Надмірне використання патернів у простих задачах (так званий overengineering) може лише невиправдано ускладнити код. Тому головне правило застосування патернів — використовувати їх лише тоді, коли існує реальна архітектурна проблема, яку вони здатні вирішити.
Ось розширений та деталізований опис обраного патерна, який ідеально підійде для глибокого розкриття теми у вашому звіті.
1.2 Опис обраного патерна
Назва патерна: Strategy (Стратегія) Тип шаблона: Поведінковий (Behavioral)
Основне призначення: Патерн «Стратегія» визначає сімейство споріднених алгоритмів, інкапсулює кожен з них в окремий клас і робить їх взаємозамінними через спільний інтерфейс. У контексті розробки «алгоритмом» може бути будь-яка поведінка: спосіб сортування даних, формат експорту звіту (PDF, CSV, XML) або логіка поведінки неігрового персонажа (NPC) у сюжетній чи пісочничній грі.
Головна мета патерна — дозволити об'єкту змінювати свою поведінку під час виконання програми, не змінюючи при цьому код самого об'єкта. Клієнтський код просто делегує виконання специфічної задачі підключеному об'єкту-стратегії.
Передумови застосування (коли використання є доцільним):
* Наявність множини споріднених класів, що відрізняються лише поведінкою. Наприклад, замість створення десятків підкласів для різних типів ворогів у грі (MeleeEnemy, RangedEnemy, MagicEnemy), ви створюєте один клас Enemy, якому передаєте різні стратегії атаки.
* Потреба в динамічній зміні алгоритмів (Runtime). Коли програма повинна перемикати логіку «на льоту» залежно від дій користувача або зовнішніх умов. Наприклад, зміна тактики персонажа з «агресивної» на «приховану» (stealth) під час проходження місії, або зміна інструменту малювання у графічному редакторі.
* Усунення «запаху коду» (Code Smell) у вигляді масивних умовних конструкцій. Якщо клас містить величезні блоки if...else або switch...case для вибору потрібного варіанту поведінки, патерн дозволяє винести кожну гілку цих умов у свій окремий клас-стратегію. Це значно спрощує читабельність основного класу.
* Приховування складних структур даних або специфічної логіки. Якщо алгоритм використовує дані, про які клієнту знати не потрібно (або небезпечно), інкапсуляція алгоритму у стратегію захищає ці дані від зовнішнього втручання.
Переваги:
* Реалізація принципу відкритості/закритості (Open/Closed Principle із SOLID). Це одна з найголовніших переваг. Ви можете додавати нові стратегії (нові алгоритми, нову зброю, нові формати тестування) до програми, не змінюючи і не ламаючи код існуючих класів. Достатньо лише створити новий клас, що реалізує інтерфейс стратегії.
* Заміна успадкування композицією. Замість того, щоб жорстко прив'язувати поведінку на етапі компіляції через ієрархію успадкування (яка часто стає громіздкою і негнучкою), патерн використовує композицію об'єктів. Об'єкт «містить» свою поведінку, а не «успадковує» її.
* Ізоляція коду (Separation of Concerns). Логіка алгоритму, його дані та залежності відокремлюються від інших об'єктів системи. Основний клас (Контекст) стає тоншим і зосереджується лише на своїй головній роботі.
* Покращення тестування. Кожну конкретну стратегію можна покрити модульними тестами (Unit Tests) ізольовано від інших частин програми.
Недоліки:
* Ускладнення архітектури (Class Explosion). Використання патерна неминуче призводить до збільшення кількості класів у проєкті. Якщо у вас є лише два-три простих алгоритми, які рідко змінюються, впровадження «Стратегії» буде невиправданим надмірним інженерним рішенням (overengineering).
* Обізнаність клієнта про відмінності стратегій. Код, який використовує Контекст (клієнт), повинен знати, чим одна стратегія відрізняється від іншої, щоб свідомо ініціалізувати Контекст правильним об'єктом.
* Витрати на комунікацію між Контекстом і Стратегією. Іноді інтерфейс стратегії вимагає передачі великої кількості параметрів із Контексту. Деякі стратегії можуть не використовувати більшість цих даних, але вони все одно будуть передаватися, що може бути неефективно. В інших випадках Контекст змушений відкривати свої внутрішні дані (робити їх публічними), щоб Стратегія могла з ними працювати.
3.3 Структура шаблона (патерна)
Опис структурних частин:
Структура патерна класично складається з трьох основних компонентів, кожен з яких виконує строго визначену роль, забезпечуючи низьку зв'язність (low coupling) системи:
1. Context (Контекст):
   * Це головний клас, з яким безпосередньо взаємодіє клієнтський код.
   * Контекст містить поле для зберігання посилання на об'єкт певного інтерфейсу стратегії (IStrategy).
   * Він не реалізує саму логіку алгоритму (наприклад, розрахунок шкоди або траєкторію атаки), а надає інтерфейс для доступу до неї.
   * Важливою особливістю Контексту є наявність методу-сетера (або передача через конструктор), що дозволяє змінити прив'язаний об'єкт стратегії під час виконання програми, тим самим змінюючи поведінку Контексту.
2. Strategy (Стратегія):
   * Це загальний інтерфейс (або абстрактний клас), який визначає контракт для всіх підтримуваних алгоритмів.
   * Зазвичай він оголошує один або декілька методів (наприклад, ExecuteAlgorithm() або Attack()), які Контекст використовує для виклику конкретного алгоритму.
   * Цей інтерфейс виступає точкою абстракції: Контекст знає лише про цей інтерфейс і нічого не знає про класи, які його реалізують.
3. ConcreteStrategy (Конкретна стратегія):
   * Це класи, які безпосередньо імплементують інтерфейс Strategy.
   * Кожен такий клас містить унікальну реалізацію алгоритму (наприклад, атака мечем, постріл з лука, використання магічного заклинання, кидок гранати тощо).
   * Конкретні стратегії абсолютно незалежні одна від одної. Їх можна легко додавати, видаляти або модифікувати, не зачіпаючи код Контексту або інших стратегій.
Опис взаємодії об’єктів:
Взаємодія між об'єктами будується за принципом делегування:
* Коли клієнтському коду потрібно виконати дію, він викликає відповідний метод Контексту.
* Контекст не виконує операцію самостійно. Замість цього він перенаправляє цей виклик прив'язаному об'єкту Конкретної стратегії.
* Передача даних: Якщо стратегії для роботи потрібні якісь дані з Контексту, існує два підходи. Контекст може передавати ці дані як аргументи методу стратегії під час виклику, або ж передати посилання на самого себе (через this), щоб стратегія могла самостійно отримати необхідні значення через публічні методи Контексту.
* Контекст працює зі стратегією виключно через абстрактний інтерфейс. Це означає, що він не знає, яка саме Конкретна стратегія зараз активна — він знає лише те, що викликаний алгоритм буде виконано.
UML-діаграма з поясненнями:
У класичній UML-нотації структуру патерна можна описати наступними зв'язками:
* Агрегація (Aggregation): Між класом Context та інтерфейсом IStrategy існує відношення агрегації (позначається лінією з порожнім ромбом на боці Контексту). Це означає, що Контекст містить об'єкт стратегії, але стратегія може існувати незалежно від Контексту.
* Реалізація (Realization): Класи ConcreteStrategyA, ConcreteStrategyB та ConcreteStrategyC реалізують інтерфейс IStrategy (позначається пунктирною лінією з порожнім трикутником, спрямованим до інтерфейсу).
* Залежність (Dependency): Client (клієнтський код) створює об'єкт певної ConcreteStrategy та передає його в об'єкт Context.
Пояснення робочого процесу за діаграмою:
1. Клієнт вирішує, яку саме стратегію потрібно використати в даний момент.
2. Клієнт створює об'єкт обраної ConcreteStrategy (наприклад, BowAttack).
3. Клієнт передає цей об'єкт у Context через конструктор або метод SetStrategy().
4. Коли клієнт викликає ExecuteOperation() у Контексту, Контекст всередині себе викликає strategy.ExecuteAlgorithm().
5. Виконується код конкретної реалізації, про яку Контекст нічого не знає.
3.4 Реалізація шаблона (патерна)
Опис реалізації мовою програмування: C#
Цей приклад демонструє використання патерна "Стратегія" в ігровому контексті. У нас є персонаж (Контекст), який може змінювати зброю (Стратегію) під час гри.
Основні етапи:
1. Створення базових інтерфейсів: Спочатку створюємо загальний інтерфейс для будь-якої атаки.
using System;


// Загальний інтерфейс Стратегії
public interface IAttackStrategy
{
    void Attack(string target);
}
2. Реалізація конкретних класів (Стратегій та Контексту): Створюємо конкретні варіанти зброї, кожен з яких по-своєму реалізує метод атаки. 
// Конкретна стратегія 1: Ближній бій
public class SwordAttack : IAttackStrategy
{
    public void Attack(string target)
    {
        Console.WriteLine($"[Ближній бій] Персонаж завдає рубаючого удару мечем по {target}! (Фізична шкода)");
    }
}

Тепер створюємо клас персонажа, який виступає в ролі Контексту. Він не реалізує логіку атаки сам, а делегує її поточній стратегії. 
// Клас Контексту
public class Hero
{
    private IAttackStrategy _attackStrategy;
    public string Name { get; private set; }


    // Конструктор дозволяє встановити ім'я та початкову стратегію
    public Hero(string name, IAttackStrategy initialStrategy)
    {
        Name = name;
        _attackStrategy = initialStrategy;
        Console.WriteLine($"\nСтворено героя '{Name}'. Початкова зброя екіпірована.");
    }


    // Метод для динамічної зміни стратегії під час виконання (Runtime)
    public void SetAttackStrategy(IAttackStrategy newStrategy)
    {
        _attackStrategy = newStrategy;
        Console.WriteLine($"-> {Name} змінює тип зброї/атаки.");
    }


    // Делегування виконання алгоритму об'єкту стратегії з передачею контекстних даних
    public void PerformAttack(string target)
    {
        Console.Write($"{Name} готується до атаки... ");
        _attackStrategy.Attack(target);
    }
}
3. Демонстрація використання: 
class Program
{
    static void Main(string[] args)
    {
        // 1. Ініціалізація Контексту з конкретною стратегією
        Hero witcher = new Hero("Відьмак", new SwordAttack());
        string currentEnemy = "Гуль";
        
        // 2. Виконання алгоритму
        witcher.PerformAttack(currentEnemy); 
        
        // 3. Зміна умов: ворог далеко. Динамічна зміна стратегії.
        currentEnemy = "Грифон у небі";
        witcher.SetAttackStrategy(new BowAttack());
        witcher.PerformAttack(currentEnemy);
        
        // 4. Зміна умов: натовп ворогів. Знову змінюємо стратегію.
        currentEnemy = "Зграя вовків";
        witcher.SetAttackStrategy(new MagicAttack());
        witcher.PerformAttack(currentEnemy);
        
        Console.ReadLine();
    }
}
