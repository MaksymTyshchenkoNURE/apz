2 ЗАВДАННЯ  
2.1 Мета роботи
Ознайомитися з архітектурними підходами у сучасних складних програмних системах, проаналізувати їхню структурну організацію, принципи масштабування, взаємодію компонентів та використані архітектурні стилі.
Відповідно до завдання необхідно: 1. Підготувати доповідь про архітектуру однієї з відомих складних програмних систем.
* 2. Обрати програмну систему для аналізу (обрано: Atlassian Jira Cloud — хмарна платформа та розподілений вебсервіс).
* 3. Дослідити її архітектуру, перехід від моноліту до мікросервісів, принципи зберігання даних та ізоляції (Multi-tenancy).


3 ОПИС ВИКОНАНОЇ РОБОТИ 
3.1 Загальні відомості про програмну систему Atlassian Jira — це одна з найпопулярніших у світі систем для управління проєктами, відстеження помилок (bug tracking) та організації процесів розробки. Історично Jira створювалася як монолітний Java-застосунок (Jira Server), проте з розвитком хмарних технологій та зростанням навантаження компанія Atlassian здійснила фундаментальний архітектурний перехід (Project Vertigo), перетворивши систему на хмарну платформу Jira Cloud, побудовану на базі глобальної інфраструктури Amazon Web Services (AWS).
3.2 Архітектурний стиль та структурна організація Сучасна архітектура Jira Cloud базується на мікросервісному архітектурному стилі (Microservices Architecture). Замість єдиного великого ядра, система розділена на сотні незалежних сервісів, кожен з яких виконує вузькоспеціалізовану бізнес-функцію (наприклад, сервіс аутентифікації, сервіс коментарів, сервіс сповіщень, сервіс пошуку тощо).
Основні структурні компоненти системи:
* Edge Routing & API Gateway (Граничний маршрутизатор): Єдина точка входу для всіх клієнтських запитів. Він відповідає за SSL-термінацію, балансування навантаження, лімітування запитів (rate limiting) та маршрутизацію до відповідних мікросервісів.
* Atlassian Identity Platform: Централізований сервіс аутентифікації та авторизації (SSO, SAML), який забезпечує єдиний доступ не лише до Jira, але й до інших продуктів Atlassian (Confluence, Bitbucket).
* Core Microservices (Обчислювальний рівень): Набір stateless-сервісів, розгорнутих у контейнерах за допомогою Kubernetes (Amazon EKS). Вони обробляють бізнес-логіку створення задач (issues), зміни статусів (workflows) та призначення користувачів.
* Search Node (Сервіс пошуку): Оскільки пошук задач за допомогою JQL (Jira Query Language) є дуже ресурсоємним, він винесений в окремий кластер на базі Elasticsearch. Дані з основної БД асинхронно індексуються для забезпечення миттєвого пошуку.
* Media & Attachments Service: Окремий сервіс для зберігання файлів та скриншотів (зокрема, звітів про дефекти), який безпосередньо взаємодіє з об'єктним сховищем Amazon S3.
3.3 Принципи масштабування та ізоляції даних (Multi-tenancy) Jira Cloud обслуговує мільйони користувачів з різних організацій, тому ключовим архітектурним викликом є масштабування та безпека даних.
* Горизонтальне масштабування (Horizontal Scaling): Оскільки мікросервіси є stateless (не зберігають стан між запитами), система автоматично створює нові екземпляри (pods) у Kubernetes під час пікових навантажень.
* Архітектура Multi-tenant (Багатоорендність): У хмарній версії різні компанії (тенанти) ділять спільні обчислювальні ресурси. Для гарантування безпеки Atlassian використовує модель ізоляції на рівні бази даних. Кожен запит супроводжується ідентифікатором tenant_id, що унеможливлює витік даних між проєктами різних організацій.
* Розподілені бази даних:
   * PostgreSQL (Amazon RDS) — для зберігання реляційних даних (користувачі, проєкти, зв'язки між задачами).
   * Amazon DynamoDB — для швидкого доступу до нереляційних даних (наприклад, конфігурації сервісів або кеш).
3.4 Взаємодія компонентів системи Взаємодія між компонентами в Jira Cloud відбувається за двома основними моделями:
1. Синхронна комунікація (REST API та GraphQL): Фронтенд системи (Single Page Application на базі React) взаємодіє з бекендом переважно через GraphQL-запити. Це дозволяє клієнту отримувати лише ті дані, які необхідні для відображення конкретного екрану (наприклад, дошки Kanban), зменшуючи обсяг трафіку. Внутрішні мікросервіси спілкуються між собою через швидкі REST-виклики або gRPC.
2. Асинхронна комунікація (Event-Driven Architecture): Для операцій, які не потребують миттєвої відповіді (відправка email-сповіщень, тригери вебхуків, оновлення пошукових індексів Elasticsearch), використовується подієво-орієнтована архітектура на базі Apache Kafka та Amazon SQS.
   * Приклад: Коли QA-інженер переводить баг-репорт у статус "Done", мікросервіс управління задачами записує подію IssueUpdated у топік Kafka. Інші мікросервіси (наприклад, сервіс сповіщень) підписані на цей топік, зчитують подію і відправляють лист автору задачі.
Приклад логічного флоу (Створення баг-репорту):
1. Користувач натискає "Create Issue" у браузері.
2. API Gateway приймає POST-запит і валідує токен через Identity Service.
3. Запит маршрутизується до Issue Service.
4. Issue Service зберігає дані в PostgreSQL.
5. Відправляється подія IssueCreated у брокер повідомлень (Kafka).
6. Search Service отримує подію і додає нову задачу в індекс Elasticsearch.
7. Клієнт отримує відповідь 201 Created.
4 ВИСНОВКИ
У результаті виконання практичної роботи було досліджено архітектуру складної розподіленої системи на прикладі Atlassian Jira Cloud.
Проаналізовано перехід системи від класичного серверного моноліту до сучасної хмарної мікросервісної архітектури. Встановлено, що використання патернів мікросервісів, оркестрації контейнерів (Kubernetes), розподіленого пошуку (Elasticsearch) та подієво-орієнтованої взаємодії (Kafka) дозволяє системі досягати високого рівня масштабованості, відмовостійкості та продуктивності. Глибоке розуміння таких архітектурних підходів є критично важливим для розуміння процесів розробки, локалізації складних дефектів під час тестування розподілених систем, а також для проєктування надійного програмного забезпечення.
